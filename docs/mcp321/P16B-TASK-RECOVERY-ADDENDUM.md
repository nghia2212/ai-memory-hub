# MCP321 P16B — Persistent Task & Auto Recovery
Date: 2026-11-25. Status: PLANNED, mandatory within V3.2.1. Integration: lead/mcp321-integration.
Read AGENTS.md, P9-P13-TELEMETRY-ADDENDUM.md, P14-P20-API-AGENT-ADDENDUM.md, P16-P19-CHAT-RESULT-ADDENDUM.md and P19A-SUBSCRIPTION-AGENT-ADDENDUM.md. Reuse existing Plan/Task/Attempt/Runner/lease/result/usage contracts. Verify actual runtime schema and backup before additive migrations; preserve all prior scope. Basic same-task recovery moves into MCP321; advanced cross-client continuity in EX33 remains required, not replaced. No competing scheduler.

## Goal
After stopping and starting Dashboard, Docker Hub, Host Runner or laptop, the user must not need to submit the original task again if durable storage is intact. Recover existing logical task, not duplicate it. Automatic continuation is conditional on verified state and permissions, not a guarantee that interrupted provider generation resumes at the exact token. External IDE may continue independently; do not assume it stopped with Hub.

## P16B.1 — Durable task and checkpoint ledger (Lead + A)
- Persist original request, conversation/plan/revision/task/attempt/session/runner IDs, dependency DAG and verified completed steps, approved actions, pending steps, provider/model, pinned Skill/MCP/Memory references, scope, limits, results and usage/budget reservations before acknowledging durable transitions. Store checkpoint at dispatch and each material step/tool/request/result boundary; atomic state and event transactions, immutable checkpoint version/provenance, idempotency keys and one DB writer.
- Capture Git HEAD/branch/worktree, approved baseline, dirty-file hashes and protected local patch/artifact references where supported, test results and pending operations. Never reset hard, overwrite or clean user work; no raw secrets/private reasoning in snapshots, logs or Git. No claim of recoverable uncommitted changes unless verified. Keep local protected data and Docker volume persistent; distinguish normal stop/start, restart, crash and deletion of volume. Document backup/restore and retention; do not delete volumes.
- Separate task execution, result delivery and recovery state. Support queued/running/interrupted/reconciling/recovery_required/paused/completed/canceled semantics using existing state model; terminal jobs not auto-rerun. Record reason, last checkpoint, timestamp, lease/heartbeat evidence, uncertain external side effects. Preserve history and real trace IDs.

## P16B.2 — Startup reconciliation and safe resume (Lead + C)
- Startup scan unfinished jobs, stale leases and pending results; bounded, idempotent and safe under concurrent startup. Acquire single authoritative lease/fencing before new dispatch; old runner must acknowledge stop, relinquish lease or be safely quarantined before replacement. Heartbeat expiry alone is not proof of termination. Verify process/session identity and worktree ownership; do not kill unrelated processes.
- If old external IDE/CLI runner still alive, reconnect/monitor/import results only through supported interfaces; do not launch duplicate job. If disconnected or state unknown, hold for reconciliation. If verified stopped, resume from last verified checkpoint using new attempt under same task, retaining approved revision and history. Resume actual session only if supported; otherwise rebuild bounded handoff context from checkpoint, not fabricated continuation. Revalidate Git dirty state, permissions, model availability, quota, budget and approval expiry. Changed state => replan or explicit user review.
- Skip only verified completed steps; check artifacts and tests remain valid. For interrupted edits inspect diff/worktree and reconcile before any further writes. No silent reset, checkout, commit, push, merge or deploy. Read-only/idempotent safe work may auto-resume under policy; non-idempotent or ambiguous effects require reconciliation/approval. Handle queued dependency readiness without duplicating completed DAG tasks.
- Managed API: record intent/request identity and reservation before call, reconcile final usage/result or provider-supported retrieval/idempotency where available. Unknown in-flight outcome => hold uncertain reservation, no blind retry or assumption of free cancellation; user-approved retry only after reconciliation/policy. Deduplicate usage, avoid replaying streaming deltas or tool calls. Preserve final response if already stored; retry delivery, not inference. No silent paid fallback.
- Graceful Stop: stop accepting new dispatch, checkpoint and flush bounded in-flight state, mark uncertain work; do not assume graceful hooks run on abrupt shutdown. Start restores state with volume intact, not an exact process snapshot. External Antigravity/Codex/Claude/Gemini support capability-specific; unsupported reconnect labeled, manual handoff allowed. No new API keys required for supported subscription execution.

## P16B.3 — Recovery policy and UI (B + D)
- Recovery modes: Manual, Automatic (only previously authorized, verified safe actions), Hybrid default (auto reconcile/reconnect and safe resume; wait approval for ambiguous side effects, new paid exposure, changed scope or unsafe writes). User may configure within existing permissions per project; never weaken security/egress. Mode changes audited. Pause/cancel semantics truthful to runtime; cancel stops future dispatch, terminal cancellation not automatically resumed.
- On startup show recovery queue in existing Work Management/Chat Workspace/Agent Control Center, not duplicate scheduler. Display project, task/plan, Agent/model, last checkpoint and completed/pending steps, old runner evidence, reason, Git state, result-delivery state and budget spent/reserved/uncertain. Actions: Resume, Reconnect, Pause, Cancel, Change Agent (explicit policy/approval), Review reconciliation; disable unsupported actions with explanation. Keep scope filters and Execution Map links; recovery events and attempt lineage visible.
- Clear Vietnamese messages; original prompt/history retained. No new task required to resume. User can explicitly retry as new attempt, distinguish from duplicating task. Show actual measured usage or unknown, no simulated live results.

## P16B.4 — Unified Windows startup and Host Brain Agent lifecycle (Lead + C + D)
- Reported defect: approved task remains queued, no execution session, Dashboard reports "Host Brain Agent chưa chạy trên host (chạy scripts/start-host-brain-agent.ps1)." Inspect existing startup/stop scripts, Compose dependencies, Windows Host Runner and scripts/start-host-brain-agent.ps1 (currently probes loopback 127.0.0.1:8084/healthz and starts Python host process). Verify actual ports, interpreter, working directory, environment, authentication and supported container-to-host connection; do not infer readiness solely from Docker running or a PID.
- Provide one supported Windows Start AI Memory Hub entry point (extend existing launcher if present; otherwise scripts/Start-AIMemoryHub.ps1), plus coordinated Stop/Restart and status commands or existing equivalents. Start Docker Desktop only if explicitly configured/authorized, wait with bounded timeout, start required Compose services preserving volumes, verify health, start/check Host Brain Agent under the intended Windows user via existing script or safely improved equivalent, verify both local health and actual Hub-to-host reachability, then reconcile queued/interrupted tasks under P16B.2. Document order/dependency constraints and adapt to actual runtime. No dependency install, firewall opening, public bind, privilege escalation or credential extraction. Do not automatically launch every optional MCP/IDE/model.
- Idempotent single-instance startup: concurrent/repeated starts must not spawn duplicate host processes or duplicate jobs. Check process identity and health, use appropriate startup lock, distinguish unrelated port occupant, stale process, missing Python, missing configuration, Docker unavailable, readiness timeout and Hub-to-host transport failure. Never kill unrelated processes; bounded retries and backoff, actionable redacted logs, exit status and component-level progress. Preserve existing Windows environment, configuration and data. No hidden API calls or paid tests.
- Dashboard System Health / Agent Control Center: separate Docker service health, Host Brain Agent availability, runner readiness and individual client/model quota; show actual last check, reason, safe instructions and copyable startup command. Offer Start/Restart Host Brain Agent only through an authenticated, explicitly authorized local management mechanism already capable of host actions or a separately reviewed narrow Windows helper; if unavailable, provide manual launcher command, not a fake button or arbitrary remote shell. Restart must not terminate active work without explicit approval and reconciliation. Block new dispatch while dependencies not ready, retain approved queued tasks and resume eligible work after verified startup according to recovery policy; no duplicate prompt submission.
- Optional Windows login auto-start (off by default, explicit opt-in, current-user least privilege, reversible and documented, no storing credentials in scheduled-task arguments). Reuse existing approved launcher, check Docker/host readiness, bounded retries; distinguish Windows login start from Docker-only Start. Disable/uninstall auto-start without deleting project data. No unattended installation or scheduler changes without user approval.
- Coordinated Stop: prevent new dispatch, checkpoint/flush, reconcile active runner behavior with user choice and existing policy; preserve volumes and unrelated IDE/CLI processes. Explicitly distinguish stopping Hub only from stopping its owned host runner. On next Start perform health checks and recovery automatically where safe. Provide clear Vietnamese messages and Windows runbook, including manual fallback using scripts/start-host-brain-agent.ps1 and health/log diagnostics.
